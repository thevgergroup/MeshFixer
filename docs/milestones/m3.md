## Spec change (v0.3): approved by the project owner

MF-OP-002 said "minimizing area then worst dihedral, after Liepa 2003". Liepa's method, which this follows, minimizes worst dihedral first, so the wording was corrected. The spec also said loops above the limit are "never silently skipped". It now spells out what happens. A selected loop that can't be filled fails by name: it's too large (the cap is now **1000**, down from 5000, because the DP is O(n³)), self-touching, or untriangulable. A whole-object run fills the rest and lists each loop it couldn't fill by ID and reason.

## Project owner's decisions (2026-11-08)

Approved:
- Spec v0.3, including the Liepa correction.
- Explicit per-loop reporting of holes that can't be filled.
- Refusing zero-area slit patches.
- Optimised test builds.

Approved with conditions:
- **The 1000-edge cap** belongs to the current algorithm. It is not MeshFixer's maximum hole size: large holes need a scalable strategy (MF-ISSUE-043).
- **3MF transforms stored but not applied** is accepted only as a temporary M3 limitation. Transform-aware rendering and picking are mandatory early in M4 (MF-ISSUE-042). Until then, multi-object editing isn't called supported.

Carried forward:
- **Slit welding/stitching** stays on the roadmap (MF-ISSUE-032).
- **Cura import isn't printability:** slicing, physical dimensions and scale are validated later (MF-ISSUE-044), and unitless OBJ import is addressed (MF-ISSUE-045).
- **Exact and Equivalent replay stay distinct:** Equivalent needs an integration-level test (MF-ISSUE-046).
- **Licence:** the project owner confirmed CC0 on the official record, so MF-ISSUE-030 is closed.

## Independent review

Verdict: "with fixes". The Critical finding and all 6 Important findings are fixed, each with a test that failed first (except I5, which strengthened a test of behaviour that was already correct):
- **C1:** CLI `--select` in later `run` steps read IDs in the edited revision, so it could silently fill the wrong hole.
- **I2:** the desktop selection wasn't tied to the active object. It drew another object's loops and failed Apply cryptically.
- **I3:** loop picking ignored occlusion, so it could select a hidden hole. Picking now also runs entirely on a worker (MF-RT-001).
- **I4:** a collinear loop was "filled" with a zero-area triangle.
- **I5:** the GUI test didn't assert which loop was picked.
- **I6:** 3MF extensions were lost silently, and prefixed extension elements were misparsed.
- **I7:** at the old 5000-edge cap the triangulation took minutes and over 1 GB.

The minor findings are MF-ISSUE-033…041.

## Found along the way

- **MF-ISSUE-029 (S1), found by the real scan.** Two holes were triangulated with a diagonal that was already a mesh edge, leaving that edge with 3 or 4 faces.
- **MF-ISSUE-031.** 3MF reading was quadratic: 554 s for 89k triangles. Export re-reads to verify, so it hung too.
- **`evidence.sh` recorded a failing benchmark as "0.00 s"**. It now stops instead.

## Rulings made during execution

- One revision per imported 3MF object. Transforms are stored and exported, but not applied in the viewport.
- Refinement works on a local patch emitted once, with a flip guard of 100× the triangle count.
- `target_of(Selection)` lives in mf-command.
- Hot geometry crates build at opt-level 2 in dev/test (real-scan tests: 160 s → 9 s).
- `reexecute` checks the operation version and restores the cursor on failure.
- The real scan's slits stay open, refused by name, rather than "closed" with zero-area triangles.
