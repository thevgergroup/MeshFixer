### Messy-model corpus (`artifacts/m4/messy/results.json`)

15 real Thingi10K models (debug-opt test harness, not release), covering non-manifold, many-hole, loose-piece and self-intersecting damage. Representative sample (`messy-inopos-131443.obj`, 637k triangles, 18 holes, non-manifold): import 0.20 s, analyse 0.53 s, whole-object fill (flat) 15 of 18 holes / 17,976 new faces in 0.32 s, 2 skipped as over the edge cap, 1 as untriangulable. Across the corpus: thousands of holes filled or refused by name (never silently skipped), with refusal reasons tied to open issues (MF-ISSUE-043 large holes, MF-ISSUE-032 slits, MF-ISSUE-051 pinched vertices, MF-ISSUE-047 tangled edges, MF-ISSUE-049 self-intersections not yet detected). The full per-model JSON is the evidence; this report doesn't restate every row.

### Fairing cost (MF-ISSUE-053, accepted for M4)

Direct solve (faer AMD ordering + a custom scalar supernodal Cholesky, deterministic across CPUs), replacing an earlier Jacobi-CG that didn't converge on the largest holes. At 1000 edges (52,408 new vertices): smooth ≈ 0.5 s (was 68 s), curvature ≈ 1.2 s (was no convergence after 332 s). 1.2 s is over the 1 s target but accepted by the owner for M4 (2026-11-10); the default style (smooth) is well under budget.

## Known limitations (stated honestly)

- **Per-vertex incremental upload and sculpt-history storage were moved to Phase 1, Task 16b.** The GPU-chunk reuse rule keeps a face chunk only if every vertex chunk it references is bitwise unchanged. For M4's own operations (fills only append) this is fine — a 5M one-hole fill uploads about 1 MB of 360 MB. It does **not** generalize to vertex-moving edits: a simulated sculpt dab on the Archaeopteryx scan re-uploads 14–29 of 31 face chunks, and the 32,768-element copy-on-write chunk size would blow the sculpt-history memory budget by 20–80× over a 1,000-stroke session. Both are registered (MF-ISSUE-074 GPU reuse granularity; the chunk-size/history-storage decision is Phase 1 P1-M4's first task) and explicitly out of scope for M4 — no M4 operation moves existing vertices in bulk.
- **At 30M triangles, undo after a whole-mesh edit re-analyses (seconds) rather than being instant.** The GPU cache is now bounded by bytes (1 GiB budget beyond the current revision, final review I5 fix), which closed an 8.6 GB worst case at 30M. The trade-off: a 30M whole-mesh edit's parent (~2 GB unshared) exceeds that budget and is evicted immediately, so undo rebuilds it from scratch. This was an explicit ruling (ledger, 2026-11-10): "accept that undo after a whole-mesh edit at 30M re-analyses (seconds) under the 1 GiB budget — the alternative is the 8.6 GB risk." Smaller edits and smaller meshes are unaffected.
- **Curvature fills are labelled less accurate above 60 edges (MF-ISSUE-055 → M5).** On the demo sphere (`artifacts/m4/demo/sphere-three-holes.obj`, R 50 mm): curvature's worst deviation from the true sphere is 0.11% at 55 edges, 2.57% at 94 edges, 11.52% at 181 edges; smooth stays at 0.17/0.19/0.51% on the same holes. The behaviour isn't monotone with hole size (it's not purely "bigger is worse"), and root cause wasn't found within the owner's timebox for Task 14a. Shipped as an honest limit rather than a silent degradation: `CURVATURE_ACCURATE_EDGES = 60`; a curvature fill above that keeps its style but is marked `curvature_less_accurate` with a plain-language warning recommending smooth, shown in the desktop status line. Smooth is the default and was the owner's preferred style on large holes at Checkpoint C.
- **Benchmarks in this report are preliminary**, as stated above: one development machine, not the MF-ISSUE-017 reference hardware, and some runs were under memory pressure.
- **CI is not yet green on the final commit** (billing-blocked; see CI state above).

## Independent review

Two whole-application reviews (final, after all 15 implementation tasks): **technical** and **UX**.

### Technical review (`final-review-technical.md`)

Verdict: **not ready to merge as reviewed** (CI red on macOS; no Critical findings). Counts: Critical 0 · Important 5 · Minor 14.

- **I1/I2 (vertex-chunk upload granularity, sculpt-history storage):** don't hurt M4 users, but block Phase 1 sculpting as built. Ruling: Phase 1 P1-M4's first task, before P1-M4 Task 17 — not an M4 blocker. See "Known limitations" above.
- **I3 (STL/OBJ export transform on the UI thread, uncancellable, could panic on overflow):** fixed in wave A — moved into the export job, cancellable, named error instead of a panic.
- **I4 (the milestone's own frame gates were red on macOS CI; `mf-desktop` wasn't built optimized for the gate):** fixed in wave A — root cause was a fairness stall in wgpu-core's device lock during `device.poll(Wait)`, fixed with a non-blocking poll loop (`wait_for_submitted`); the gate now runs `mf-desktop`'s timing tests `--release`; two GUI-test flakes (wall-time vs input-time waits) also fixed.
- **I5 (GPU cache bounded by count, not bytes — up to ~8.6 GB at 30M):** fixed in wave A — LRU, byte-budgeted (1 GiB default beyond current revisions), with the accepted 30M-undo trade-off above.
- **14 Minor findings:** registered as MF-ISSUE-065…073, 077…080 (M5, two marked "M4 follow-up (trivial)"), or fixed directly where trivial.

### UX review (`final-review-ux.md`)

Verdict: "mostly yes" to "could a Meshmixer/Fusion 360 user repair a messy scan without guidance" for holes and loose pieces; broke down in four places before the fix round. Counts: Critical 1 · Important 8 · Minor 11.

- **C1 (dead ends on cracks, tangled edges, very large holes):** fixed in wave B — every refused defect now has a verdict, a stated limit, and a next action; see "No dead ends" gate above.
- **I1 (curvature warning lost on a targeted fill) / I2 (import warnings never shown):** fixed in wave B — the warning survives a fill and a batch; import warnings get their own readable window.
- **I3 (intentional openings stayed hole-orange) / I4 (one thing, several names) / I5 (laptop windows: panels ate the view) / I6 (hole markers off by default) / I7 (a pinched hole was offered Fill):** all fixed in wave B — new `OPENING` colour token; consistent naming; collapsible panels (Cmd/Ctrl+\\) tested at 1280×720 and 1024×640; markers on by default; Fill no longer offered where it can't work.
- **I8 (needs a tool framework before Phase 1 tools land):** ruled out of scope for M4 — it's Phase 1 structure (P1-M1), needed either way.
- **11 Minor findings:** registered as MF-ISSUE-056…064 (M5) or fixed directly where trivial (thousands separators, consistent "Analysing…", disabled Apply when nothing would fill).

- faer (MIT) approved as a new dependency for sparse fairing solves (MF-ISSUE-053).
- Heavy/timing/5M tests and fuzzing run **on demand only** (owner ruling, 2026-11-09): push/PR CI runs the fast suite; `heavy.yml` and `fuzz.yml` are `workflow_dispatch` (plus PR labels `run-heavy`/`run-fuzz`, since they aren't on the default branch).
- Task 14a (curvature on large holes) timeboxed by the owner at 45 minutes: ship a labelled limit over continued root-causing; MF-ISSUE-055 moved to M5.
- The GPU cache's 1 GiB-over-current budget (final review I5) was an explicit trade against the 8.6 GB worst case; the 30M-undo re-analysis cost is accepted, not hidden.
- Phase 1 modelling plan (gizmo → booleans → split/pegs → sculpting → mixing) written and committed alongside M4 (`docs/superpowers/plans/2026-11-10-phase1-modelling-tools.md`), with D1–D19 decisions (manifold-rust, robust, spade) approved; not part of M4's scope.
